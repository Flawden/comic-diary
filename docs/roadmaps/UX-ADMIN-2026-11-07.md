## 1. Product goal

Comic Diary is a platform for reading graphic works, maintaining a personal reading diary, tracking chapter progress, and managing a shared comic catalog.

The goal is not merely to have working features. The goal is to deliver a coherent product that:

- readers can use comfortably;
- administrators can manage without fighting the interface;
- makes adding and updating comics straightforward;
- protects private user data and isolates accounts;
- behaves reliably on desktop and mobile;
- is good enough that we are proud to show it to other people.

**Core principle: technically working does not automatically mean product-ready.**

The public release is intentionally postponed. First, finish and polish the functionality that already exists, especially the administration experience and reader-facing UX.

### 2.3 Critical reading UX regression fixed

A bug was found while using the site: after choosing “do not ask again” in a native confirmation flow, the user could no longer reliably remove a chapter's read mark.

The fix replaced the native `window.confirm` path in `ChapterReadingPanel` with a project-owned confirmation component.

Implemented:

- explicit confirmation dialog;
- clear warning that removing the read mark also removes the chapter rating;
- cancel action that leaves the state unchanged;
- explicit confirm action;
- regression test;
- CI step for the regression test.

Commit: `428ecbe` — `fix(ux): replace native unread confirmation`.

## 3. Design direction

### 3.1 Visual reference

The target is the dark, atmospheric **Comic Studio** concept reviewed on 2026-11-07.

Key visual elements:

- deep emerald / forest-green base;
- muted olive and pale sage accents;
- warm, readable typography;
- restrained borders and shadows;
- compact cards and controls;
- clean icons;
- subtle motion rather than decorative animation everywhere;
- an atmospheric forest illustration in the left navigation panel;
- dark overlay / gradient over the illustration so navigation remains readable.

The forest illustration is a deliberate part of the visual identity. It should eventually be stored as a real optimized image asset (for example WebP), not approximated entirely with CSS gradients.

### 3.2 UX principles

1. **Progressive disclosure:** show essential controls first; reveal secondary settings when requested.
2. **Low visual noise:** avoid giant forms and repeated explanatory text.
3. **Clear hierarchy:** users should understand where they are and what they are editing.
4. **Stable context:** selecting another comic should not feel like navigating away to a different application.
5. **Safe actions:** destructive or consequential operations must be explicit and understandable.
6. **Visible system state:** loading, saving, success, failure, and unsaved changes must be communicated.
7. **Responsive by design:** desktop, laptop, tablet, and mobile layouts must all be considered.
8. **Preserve working business logic:** UX work should not trigger unnecessary rewrites of stable modules.

### 3.3 Target Admin Studio layout

The intended desktop composition has three working zones:

1. **Left navigation:** brand, forest background, admin navigation, administrator profile at the bottom.
2. **Catalog pane:** search, filters, sorting, comic cards, status, cover, chapter count, quick actions.
3. **Editor pane:** selected comic and its editing workspace.

The editor keeps the three main tabs:

- Metadata;
- Chapters;
- Publication.

Chapters must remain in the Chapters area. They must not spill into the metadata form or create one enormous vertically-scrolling editor.

On smaller screens, the three-zone layout should collapse into a deliberate responsive flow rather than simply shrinking every column.

### Phase 4 — Chapter Studio

**Status: PLANNED — HIGH PRIORITY**

This phase addresses one of the largest current admin UX problems: adding and managing chapters is too cumbersome.

#### 4.1 Per-comic grouping label

Different works use different structural divisions. The current generic “Том” label is not suitable for every comic.

Add a per-comic grouping configuration with options:

- Том;
- Арка;
- Книга;
- Сезон;
- Часть;
- Без группировки;
- Собственное название.

Examples:

- “Том 1” for a volume-based work;
- “Арка 1” for an arc-based work;
- “Книга 1” for a book-based work.

The chosen label must be reflected consistently in both the admin interface and reader-facing comic page.

The setting belongs to the comic, not globally to the entire catalog.

**Compatibility requirement:** preserve existing group data and existing works. Define a safe default / migration behavior before changing the data model.

#### 4.2 Chapter list

Prefer compact, scannable rows over large cards.

Show the information that helps administer a chapter:

- chapter code;
- chapter title;
- group label / group number;
- chapter type;
- publication status;
- release date;
- order;
- revision information where relevant.

Keep search and useful filters available without taking excessive vertical space.

#### 4.3 Chapter actions

Support the existing operations with a clear interface:

- add chapter;
- edit chapter;
- archive chapter;
- reorder chapter;
- move chapter where supported;
- search and filter;
- manage revisions;
- create a new revision of an existing chapter.

Do not introduce permanent deletion unless its data consequences, dependencies, and recovery behavior have been explicitly designed.

#### 4.4 Adding chapters

Design separate, understandable paths for:

- creating a brand-new chapter;
- creating a new revision of an existing chapter;
- adding multiple chapters in one operation.

Improve:

- automatic suggestion for the next order value;
- optional chapter code;
- optional title;
- group selection;
- chapter type;
- status;
- release date / expected-date precision;
- clear validation;
- success and failure feedback.

Do not make the user fill every possible field.

#### 4.5 Revision safety

- preserve the relationship between revisions;
- preserve reading history according to existing business rules;
- make it obvious whether the user is editing a chapter or creating a replacement revision;
- explain consequential actions before saving.

**Acceptance criteria**

- a routine chapter addition is quick;
- the list remains compact;
- grouping terminology is correct for each comic;
- revisions cannot be confused with unrelated new chapters;
- existing reading-history behavior is preserved.

### Phase 5 — Publication Studio

**Status: PLANNED**

Make publication and visibility settings independent and understandable.

**Release status**

Use the statuses already supported by the application, such as:

- ongoing;
- completed;
- paused;
- other existing supported values.

Do not invent new database enum values without checking the current schema and business logic.

**Visibility settings**

Keep separate concepts separate:

- visible in catalog;
- hidden from catalog;
- available on the site / public page.

The release status of a work is not the same as its visibility in the catalog.

**UX**

- clear toggles or controls;
- concise explanation of each setting;
- warning where a change has significant public consequences;
- explicit save state;
- public-page preview / link.

### Phase 6 — Comic Creation & Import UX

**Status: PLANNED — HIGH PRIORITY**

Adding a new comic should no longer feel like completing a giant administrative form.

**Creation flow**

Use a guided, compact process:

1. basic information;
2. cover;
3. optional additional metadata;
4. create / save draft;
5. add chapters.

Allow optional information to be skipped. Avoid blocking creation on fields that are not truly required.

**Import flow**

Improve the existing import workflow rather than replacing it without cause:

- clear entry point;
- understandable import states;
- preview of incoming data;
- validation and duplicate/conflict warnings;
- clear error messages;
- explicit confirmation before applying changes;
- ability to continue editing manually after import.

**Acceptance criteria**

- a new comic can be created without navigating a long form;
- the user understands what will be imported or changed;
- failed imports do not leave ambiguous partial state;
- existing import capabilities continue to work.

The unread confirmation regression fix is a baseline; test related flows to prevent similar preference / confirmation bugs.

#### Personal library

**Known UX gap:** users can change a comic's reading status but currently lack a clear “Remove from my library” action.

Add an explicit action to remove a comic from the current user's personal library.

Important distinctions:

- removing from a personal library must not delete the shared comic from the public catalog;
- it must affect only the current user's relationship / personal state;
- consequences for personal reading history, notes, and ratings must be defined before implementation;
- provide confirmation if the operation removes or changes personal data.

## 6. Development workflow and safety rules

Current stage is pre-release development. The project owner has chosen to work directly in `master` for now because the product is not yet in public or closed beta.

Until the workflow changes:

- work primarily in `master`;
- use small, reviewable patches;
- inspect worktree state before applying changes;
- never overwrite uncommitted user changes;
- run `git diff --check`;
- run relevant tests and typecheck;
- inspect the resulting diff before committing;
- verify CI before deployment;
- do not modify production without a tested plan and backup;
- keep production data and disposable test data strictly separated.

Before closed beta, move to a stricter release workflow:

- feature branches;
- pull requests;
- required CI;
- review before merge;
- controlled deployments and rollback.

### Implementation approach

- preserve stable business logic;
- separate visual refactoring from data-model changes where possible;
- introduce database migrations only when required and with compatibility planning;
- make destructive actions explicit;
- test both the happy path and cancellation / failure paths;
- verify the real interface after deployment.
