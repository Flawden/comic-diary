## 2. Observed gaps and limits of evidence

1. **No public password-reset flow found in the selected sources:** no reset-request/consume endpoints, recovery-token table, or 'Forgot password' link in the login page.
2. **No email verification visible in the selected auth source:** registration immediately creates active authenticated users; `users` has no verified-email field. Email address currently identifies an account, but ownership is not established at signup.
3. **No transactional email sender identified:** `package.json` lacks obvious SMTP/provider client dependencies, and the provided file inventory has no clear mail-transport module. This does *not* prove there is no out-of-band production mail service; verify separately before choosing one.
4. **Admin emergency recovery is a different capability** from self-service email recovery; do not wire public requests to administrative recovery scripts.
5. No live mail sender/DNS/provider/domain settings are in this archive. Do not print or ask for secrets in chat. The audit is of selectively redacted snapshots, not byte-for-byte live code.
6. Exact email ownership policy for existing unverified accounts and staff accounts is still an **explicit product/security decision**. Do not assume an email string is proof of ownership.

## 3. Proposed secure AUTH-01 contract (NOT YET IMPLEMENTED)

### Recovery request

- UI `/forgot-password` and POST `/api/auth/password-reset/request` (names provisional).
- Validate normalized address; return the **same generic acknowledgement** whether the account exists, is inactive, or has no password. Do not reveal delivery status or staff role.
- Reuse same-origin validation, fail-closed request limits, bounded JSON and no-store responses. Add abuse limits across **trusted client IP** and **normalized account/email identifier**, with short resend cooldown; establish exact limits during implementation.
- For eligible accounts only, generate a **cryptographically random 32-byte URL-safe token**, store only SHA-256 digest, account ID, expiry, created time, consumed marker; default proposed TTL **20 minutes**. Replacement requests should invalidate prior pending tokens according to a documented policy.
- Determine the email transport first. It must be provider-agnostic in application code, with explicit failure behavior and no token logging. Mail delivery to a controlled test mailbox must pass before enabling production links.
- Construct absolute links from `COMIC_DIARY_PUBLIC_ORIGIN` or another validated canonical origin, **never** request Host or forwarding headers. Avoid third-party assets on token-entry pages; set strict Referrer-Policy and no-store; scrub URL tokens promptly.

### Recovery completion

- GET reset page must not change the password. POST completion accepts token + new password and confirmation with the existing strength rules.
- Validate token hash, expiry, account eligibility and unused status. Prevent reuse and race via transaction and row locks / conditional updates.
- In **one transaction**, consume token, update password with existing Argon2id implementation, and revoke all current sessions. **Do not auto-login** after an email reset; send the user to sign in using the new password.
- Invalid/expired/used token returns a safe error and offers another recovery request; never reveal the user's email, role, or existence through reset errors.
- Do not alter `user_comics`, chapter progress, ratings, notes, images, or roles. Never run a browser test against production DB.
- Consider notifying the account email after successful password change without putting secrets into the notification.

### Email ownership is a gate, not an afterthought

- Current registration grants access without proof of mailbox ownership. Before enabling self-service recovery for unverified/legacy accounts, define and test the ownership/claim policy to prevent email-address squatting or unintended account takeover. A separate verification flow for new registrations and safe treatment of existing accounts are likely needed.
- Staff/ADMIN accounts merit a distinct reviewed recovery policy and audit trail; do not casually treat them exactly as newly registered USER accounts.
- Do not use knowledge of an email alone to reset a password; a valid single-use token delivered to that mailbox is mandatory, along with the legacy account policy above.

## 4. Proposed implementation order

1. **AUTH-01A — contract and CI tests:** finalize policy for existing emails, staff and failure responses; add negative tests for account enumeration, token expiry/replay, rate limits, concurrent consumption, session revocation, and no-diary-data mutation.
2. **AUTH-01B — additive schema and service:** new recovery-token table and Drizzle migration (inspect migration journal/master before assigning next number), token issue/consume code; no public route and no real mail yet.
3. **AUTH-01C — transport and safe request endpoint:** choose supported transactional email provider, domain verification, secret configuration outside Git; injectable mail adapter, mock provider in CI; do not activate public flow until send/expiry/retry checks pass.
4. **AUTH-01D — UX and acceptance:** forgot-password and reset screens in tea/paper/night, mobile browser scenarios, keyboard/accessibility, smoke test to a controlled inbox and manual acceptance.
5. **Release gate:** green feature CI and PR checks, approval before merge, exact master SHA deploy smoke and `DEPLOYED` check; no manual live DB testing with disposable fixtures.

## 5. Acceptance checklist

- [ ] Same generic recovery-request response for existent/nonexistent/inactive accounts.
- [ ] Email address ownership/legacy-account policy explicitly approved and tested.
- [ ] 32-byte tokens hashed at rest, time-limited and one-time; no raw token logs.
- [ ] Concurrent redemption permits only one successful change.
- [ ] Account password changes and all prior sessions are revoked atomically.
- [ ] All reading history, ratings, notes, and privileges remain intact.
- [ ] Rate limiting and failure behavior safe if backend or mail provider is unavailable.
- [ ] Sender domain authenticated and end-to-end delivery verified to test mailbox.
- [ ] Three-theme and narrow-screen UX accepted; browser QA uses a disposable DB.
- [ ] No secrets, tokens, or personal emails in test artifacts and CI logs.
- [ ] User approval for merge and production verification captured.
