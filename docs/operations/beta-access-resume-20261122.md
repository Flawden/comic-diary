# Повторная проверка доступа к закрытой бете

Исправляется тупиковый экран `/beta-wait`: раньше он всегда показывал ожидание, в том числе уже допущенному аккаунту или после выключения ограничения. Сейчас страница читает актуальную policy, сессию и отметку beta_participant; разрешённый пользователь перенаправляется в каталог. Для ещё не допущенного аккаунта показан его собственный email, чтобы отличить старый аккаунт от зарегистрированного по другому приглашению. Гость получает предложение войти. «Проверить доступ» делает обычную полную GET-навигацию и не использует сохранённый Router Cache.

Успешный вход выполняет полную навигацию, как и выход из аккаунта: старые предзагруженные отказы и состояние прежней личности не переносятся. `/beta-wait` исключён из адресов возврата после успешного входа. Защита от внешнего redirect сохранена.

Основной допуск в Proxy не ослабляется: ADMIN, а также активный пользователь с действующей полной сессией и beta_participant=true проходят. Рамка не даёт допуск отдельно. Pending/inactive/expired и неучастники остаются закрыты. Схема, membership, награды, пароли и существующие сессии не изменяются исправлением. Миграций и изменений AUTH/gates/pilot/recovery не требуется. Production policy и отметки пользователей агент не переключает.

Диагностика исходной production-сборки на изолированном PG17: legacy USER с участием и старой сессией получает root 200 и API 200; уже открытый `/beta-wait` ошибочно оставался 200 с ожиданием. После исправления тот же `/beta-wait` даёт 307 в каталог. Это подтверждённый дефект возобновления доступа. Если свежая навигация в каталог всё ещё закрыта, следует проверить именно аккаунт/сессию отказавшего браузера; наличие другой учётной записи в админском списке не авторизует текущую сессию.

Регрессия запускает скомпилированный `.next/standalone/server.js`, а не custom Next host: старые legacy и новые verified аккаунты, старая сессия, guest denial → реальный LoginForm → каталог без cached denial, выдача/отзыв/повторная выдача, обновление уже открытого ожидания, выключение ограничения, Tea/Paper/Night и 320/390/1440. Проверяются отрицательные pending/inactive/expired/неучастники, сохранность сессии, неизменность AUTH gates/generations/pilot. Все AUTH OFF, Resend key отсутствует, внешний server HTTP блокируется test-only preload. Для loopback HTTP fixture проверяется наличие Secure в реальном login response, и только тестовый browser relay снимает Secure при воспроизведении cookie; production Cookie не меняется. Полный HTTPS production deploy остаётся штатным. При failure deploy/внешнего HTTPS — остановиться без ручного rollback и повторного deploy.
