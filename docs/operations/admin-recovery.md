# Bootstrap первого ADMIN и аварийное восстановление

Этот документ описывает операторский механизм создания первого администратора
и аварийного восстановления административного доступа Comic Diary.

Механизм не имеет публичного HTTP endpoint и не использует временный
bootstrap-secret.

Для его выполнения требуется административный shell-доступ к production VPS
и право оператора управлять Docker на сервере.

## Главный инвариант безопасности

`scripts/admin-bootstrap.mjs` разрешает изменение административных полномочий
только тогда, когда в базе данных нет ни одного активного пользователя с ролью
`ADMIN`.

Перед проверкой этого условия скрипт получает тот же PostgreSQL advisory lock,
который используется обычным доменным механизмом управления аккаунтами.

Если хотя бы один активный `ADMIN` существует, операция завершается отказом:

```text
BOOTSTRAP_REFUSED=ACTIVE_ADMIN_EXISTS
```

В таком случае:

- новый пользователь не создаётся;
- существующий пользователь не повышается;
- отключённый пользователь не активируется;
- пароль не изменяется;
- существующие сессии не затрагиваются.

Благодаря этому один и тот же операторский инструмент используется для двух
случаев:

1. создание первого ADMIN на новой установке;
2. аварийное восстановление, если система осталась без активного ADMIN.

Этот механизм не является обычным интерфейсом управления ролями.

## Восстановление существующего пользователя

Если указанный email уже принадлежит пользователю и активных ADMIN нет,
bootstrap:

- сохраняет существующий `users.id`;
- устанавливает роль `ADMIN`;
- устанавливает `is_active = true`;
- записывает новый Argon2id password hash;
- отзывает все существующие сессии этого пользователя.

Все данные, связанные с существующим `users.id`, сохраняются.

В частности, записи `user_comics` остаются привязаны к тому же аккаунту.

Если пользователя с таким email нет, создаётся новый активный ADMIN.

## Работа с паролем

Пароль передаётся bootstrap-скрипту только через stdin.

Нельзя передавать или хранить пароль:

- в аргументе командной строки;
- в environment variable;
- в скрипте, который попадёт в Git;
- в proof-логах;
- в incident report;
- в истории команд в открытом виде.

В PostgreSQL сырой пароль не сохраняется.

Хранится только Argon2id hash.

## Предварительная production-проверка

Подключиться к production VPS интерактивно.

```bash
cd /opt/comic-diary

sudo -v

sudo docker compose \
  --env-file .env \
  -f compose.yml \
  exec -T db \
  sh -lc '
    psql \
      -U "$POSTGRES_USER" \
      -d "$POSTGRES_DB" \
      -qAt \
      -v ON_ERROR_STOP=1 \
      -c "
        SELECT '\''ACTIVE_ADMINS='\'' || count(*)
        FROM users
        WHERE role = '\''ADMIN'\''
          AND is_active = true;
      "
  '
```

Для first-admin bootstrap или аварийного восстановления продолжать можно только
если получено:

```text
ACTIVE_ADMINS=0
```

Если существует хотя бы один активный ADMIN, необходимо использовать обычный
authenticated account-administration boundary.

## Создание первого ADMIN / аварийное восстановление

Сначала отдельно подтвердить sudo-доступ:

```bash
sudo -v
```

Затем выбрать email и ввести новый пароль интерактивно:

```bash
cd /opt/comic-diary

IFS= read -r -p "Admin email: " ADMIN_EMAIL
IFS= read -r -s -p "New admin password: " ADMIN_PASSWORD
printf '\n'

printf '%s\n' "$ADMIN_PASSWORD" |
  sudo docker compose \
    --env-file .env \
    -f compose.yml \
    exec -T app \
    node scripts/admin-bootstrap.mjs \
      --email "$ADMIN_EMAIL"

unset ADMIN_PASSWORD
unset ADMIN_EMAIL
```

Успешный результат содержит один из вариантов:

```text
ACTION=CREATED_ADMIN
```

или:

```text
ACTION=PROMOTED_EXISTING_USER
```

и обязательно:

```text
ADMIN_BOOTSTRAP=PASS
ROLE=ADMIN
IS_ACTIVE=true
PASSWORD_HASH=ARGON2ID
RAW_PASSWORD_PERSISTED=NO
```

## Проверка сразу после восстановления

Production recovery нельзя считать завершённым только потому, что CLI вернул
`ADMIN_BOOTSTRAP=PASS`.

После операции необходимо:

1. убедиться, что существует хотя бы один активный ADMIN;
2. войти через обычную страницу `/login`;
3. получить обычную пользовательскую session cookie;
4. проверить этой сессией защищённый `ADMIN_USERS` boundary;
5. убедиться, что USER не получил административных полномочий;
6. убедиться, что EDITOR не получил административных полномочий;
7. не сохранять сырой recovery-пароль в proof-логах.

Таким образом конечная цепочка проверки выглядит так:

```text
bootstrap
→ password login
→ normal session
→ ADMIN_USERS authorization
```

## Повторный bootstrap

Не нужно специально запускать второй bootstrap в production ради доказательства
защиты.

Отказ при существующем активном ADMIN уже проверяется изолированными
интеграционными тестами.

Повторный production bootstrap допустим только тогда, когда реально возникла
аварийная ситуация и число активных ADMIN снова стало равно нулю.

## Защита последнего активного ADMIN

Обычный account-administration domain не позволяет:

- понизить последнего активного ADMIN до USER;
- понизить последнего активного ADMIN до EDITOR;
- деактивировать последнего активного ADMIN.

Эта проверка выполняется внутри транзакции.

Account administration и bootstrap используют один общий PostgreSQL advisory
lock, поэтому конкурентные операции не могут одновременно удалить последнего
активного ADMIN и выполнить recovery поверх устаревшего состояния.

## Границы аварийного восстановления

Этот механизм восстанавливает только административные полномочия аккаунта.

Он не предназначен для восстановления после:

- повреждения PostgreSQL;
- потери database volume;
- повреждённых или незавершённых migrations;
- компрометации VPS;
- компрометации Docker image;
- потери инфраструктурного доступа.

Такие ситуации требуют отдельного infrastructure/database recovery до изменения
полномочий пользователей.
