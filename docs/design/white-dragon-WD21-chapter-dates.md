# WD21 — даты выхода глав

## Что означает каждая дата

- **Вышла** (`chapters.released_at`, nullable): фактический день публикации у первоисточника. Редактор вводит дату в формате дня; сервер сохраняет полдень UTC, чтобы локальная часовая зона не сдвигала календарную дату. Старые timestamp не меняются при редактировании других свойств.
- **Ожидается** (`chapters.expected_release`, nullable): редакторское ожидание с точностью `YYYY` / `YYYY-MM` / `YYYY-MM-DD`. Это *не* дата публикации, и сервер не переводит главу в `RELEASED` по наступлении срока.
- **Добавлена в Чайную** (`chapters.created_at`): системное время создания записи, без ручного изменения.

Миграция `0023` только добавляет nullable-колонку. Старые `released_at` не обнуляются и не «исправляются» автоматически: часть записей могла получить дату добавления вместо исторического дня выхода. Такие главы нужно выборочно проверить по первоисточникам.

## Проверка перед закрытием

1. Создать `SCHEDULED` с месяцем (`2026-11`), убедиться в отображении «ноябрь 2026 г.», отсутствии даты выхода и неизменности статуса.
2. Создать `SCHEDULED` с годом (`2027`) и точным днём (`2027-12-03`), проверить сохранение точности после перезагрузки.
3. Создать `RELEASED` с историческим днём и без даты; ни один вариант не должен подставить «сегодня».
4. Перевести запланированную главу в опубликованную: ожидаемая дата очищена, фактическая записана только при явном вводе.
5. Поправить код/название опубликованной главы: `released_at` (включая точное время старых записей) и `created_at` не меняются.
6. Проверить новую редакцию, архив, отметки читателей, оценки, экспорт дневника, обработку несуществующей даты, день/месяц/год на мобильном экране.
7. Проверить чистую и повторную миграцию PostgreSQL в CI, затем production deployment.

Планируемые даты на публичной вкладке обновлений появятся в WD18. WD21 управляет датами в админке и предоставляет их в read-model/API; он не рассылает уведомлений и не запускает публикацию.
